# 风险与漏洞评估 · cs-debug-toolkit v1.3.0

> 评估日期：2026-09-25 ｜ 范围：本工具包（`scripts/` 脚本、`cli/` 命令、`skill/` 技能、构建与分发链路）
> 方法：代码审读 + 实际发布链路复盘（v1.2.0 上线过程）+ 泄漏扫描实测 ｜ 结论用语：`已修复` / `待决策` / `已缓解`

## 0. 摘要

- **最严重的历史问题**：v1.2.0 发布时，**公开仓库里带出了真实人名、机器名、买家账号、客户品牌名、
  生产环境 32 位 ID 示例与个人路径**——根因是**构建脚本只扫「分发包」，没扫「整棵源码树」**，
  而仓库里 `docs/`、`tests/`、`skill/` 等文件不入包却会公开。**v1.3.0 已全量修复并加了自动门。**
- 本次共梳理 **5 类 17 项**风险：**4 项已修复**、**8 项已缓解（有规程约束）**、**5 项待决策**（涉及管理/产品选择）。
- 工具链的**只读定位**成立（无写命令路径），主要风险集中在**凭据保管**与**客户数据外流**两端。

## 1. 数据与隐私风险

| # | 风险 | 现状与影响 | 处置 |
|---|---|---|---|
| 1.1 | **公开仓库内容泄露**（真实人名/买家昵称/品牌名/生产 ID/个人路径） | v1.2.0 实际发生；已公开的内容无法"收回"，只能覆盖 | ✅ **已修复**：全树替换为假值/占位；新增 `scripts/leak_scan.py` 扫 `git ls-files` 全树；本地模式表扩到 28 条（含客户名与机器名 regex） |
| 1.2 | **证据包/报告含客户数据**（店铺名、会话 ID、出口 IP、cookie、订单号） | 报告与截图属内部交付物，外发即泄露 | ⚠️ **已缓解**：技能约束"只读 + 内部留存"；`docs/REPORT_STANDARD.md` §5.2 要求外发前脱敏；结案四步清理（归集→核对→删除→收口） |
| 1.3 | **截图内含客户信息**（买家昵称、订单、倒计时水印） | 截图是"客户在等"的关键证据，不能不留 | ⚠️ **已缓解**：证据区只留 `screenshots\`；外发前须打码/裁剪（人工步骤，未自动化） |
| 1.4 | **`temp/` 中转区残留** | 排查中间产物含原始 json/日志，长期堆积会形成本地数据湖 | ⚠️ **已缓解**：`temp/` 定位为临时中转，结案清零（§5.1 B）；无自动过期机制 |

## 2. 凭据与访问控制

| # | 风险 | 现状与影响 | 处置 |
|---|---|---|---|
| 2.1 | **SLS AK 明文落盘** `channels.json` | 已 gitignore，但本机文件系统可见；AK 泄露=可读全部日志 | ⚠️ **已缓解**：只用**只读**子账号 AK（`log:GetLogStoreLogs`）；建议 90 天轮换 + 按项目分 AK |
| 2.2 | **cs-cli 凭据** `~/.cs-cli/credentials.json`（`accessToken` 用于截图签名下载） | 脚本会读取该文件换签名 URL | ⚠️ **已缓解**：仅本机、仅内部工具；建议限制家目录权限、勿在共享账号下运行 |
| 2.3 | **ECD AK 与 SLS AK 混用** | ECD AK 具备**远程执行**能力（`RunCommand`），风险高于只读 SLS | ✅ **已隔离**：`ecd.json` 与 `channels.json` 分文件管理；**ECD AK 不随包分发** |
| 2.4 | **GitHub token 出现在对话/命令行** | token 只 `repo` scope；但贴到对话即等于暴露 | ⚠️ **已缓解**：仅用环境变量注入、不写入脚本；**发版后必须撤销重建**（每次发布后都做） |
| 2.5 | **签名下载 URL 可复用** | `sign-url` 换取的 OSS 链接有时效 | ✅ 已按短时效使用；不外传 URL、不写入报告 |

## 3. 执行安全与只读边界

| # | 风险 | 现状与影响 | 处置 |
|---|---|---|---|
| 3.1 | **只读承诺靠约定、未在代码层强制** | `csapi.py` 透传任意 cs-cli 子命令；写命令（`sa update`/`faq update`）理论上可被调用 | 🟡 **待决策**：加**只读子命令白名单**（拒绝 `update/delete/create` 类）——建议 v1.4 落地 |
| 3.2 | **SQL 原样拼装**（`--sql-where`） | 只读查询，无注入提权面；但 `--search "*"` 全量扫描会**刷爆 SLS 配额/费用** | ⚠️ **已缓解**：文档写明代价与限窗；建议 SDK 侧加"时间窗必填 + 行数上限"硬约束 |
| 3.3 | **输出路径由参数决定**（`--output`） | 可写到任意目录（含版本库内） | 🟡 **待决策**：限定输出根目录白名单（`temp/` 或交付区） |
| 3.4 | **子进程调用** | 全部 `subprocess` 无 `shell=True`，无命令注入面 | ✅ 无风险（审定通过） |
| 3.5 | **ECD 远程拉起**（`host-pull`） | 具备在远端主机执行脚本的能力 | ⚠️ **已缓解**：仅限授权人员、AK 单独保管、脚本只读采集 |

| 4.1 | **Python 依赖未锁版本**（`aliyun-log-python-sdk`） | 上游破坏性变更会打断工具链 | 🟡 **待决策**：`requirements.txt` 固定主版本区间 |

## 5. 结论质量与误判风险（业务风险）

| # | 风险 | 现状与影响 | 处置 |
|---|---|---|---|
| 5.1 | **签名自动匹配假阳性** | 通用告警文案会被误认为某型故障（如"主窗口未找到"） | ⚠️ **已缓解**：签名只产出**候选**，结论仍需人工判定；新增签名均带 `min_count` 或标为参考条目（17 条自动匹配 / 9 条参考） |
| 5.2 | **口径混淆**（平台 vs 服务端）误判为故障 | 历史上多次把平台口径假象写成系统故障 | ✅ **已固化**：`cs-fault-playbook` 第 12/22 型 + 报告规范要求写明口径差异 |
| 5.3 | **把相关性当因果** | 时间相邻 ≠ 因果 | ✅ **已固化**：报告骨架要求每个节点写"**不能**推出什么"；结论强制三段式（B 段未证候选不得省略） |
| 5.4 | **ID 省略导致不可追溯** | 短码无法二次检索 | ✅ **已固化**：全篇完整 32 位 ID（MD + HTML 双写） |

## 7. 待决策项（需管理/产品判断）

1. **公开范围**：仓库目前为 **public**，含产品命名（SLS project/logstore 名）与内部流程文档。
   若视为不可公开，应转 private（代价：安装需认证，需配套内网分发）。
2. **只读白名单**：是否在 `csapi.py` 加子命令白名单（拒绝一切写操作）——建议做，代价小。
3. **AK 形态**：SLS 是否改用 **STS 临时凭证**（有效期 1h，需刷新机制）。
4. **证据留存时长**：截图与报告在交付区的保留策略（当前无上限）。
5. **分发校验**：Release 是否附 `sha256` 并要求安装方校验。

## 8. 复发防控清单（每次发版/结案照做）

- [ ] 发版前：`python scripts/leak_scan.py`（源码树）+ `build_cli.ps1` / `build_package.ps1`（分发包）**双门全绿**
- [ ] 新增示例/文档时：ID 用假值、路径用占位、账号用示例名
- [ ] 每个案例结案：四步清理（归集 → 核对 → 删除 → 收口），`temp/` 清零
- [ ] 每次发布后：**撤销并重建 GitHub token**（对话里出现过的 token 一律作废）
- [ ] 每季度：轮换 SLS AK、复核依赖版本、重跑一次本评估
